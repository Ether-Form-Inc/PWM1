# Overview
This repo contains the firmware to be flashed onto EFI's can\_to\_pwm hardware to respond to the DroneCAN protocol, which is the current protocol maintained by PX4. The node is built on [libcanard](https://github.com/dronecan/libcanard) with C code generated from the DroneCAN DSDL definitions, so it has no other CAN stack dependency.

This repo is written to be compatible with Ether Form Incorporated (EFI)'s  can\_to\_pwm Rev B+. 

![Board](images/Can_to_pwm.png)

This board supports 4 PWM outputs (J4) controlled via DroneCAN's ArrayCommand (1010) for servo commands or RawCommand (1030) for motor commands. The outputs are generated by a PCA9685 (12-bit, 50 Hz) which the STM32 drives over I2C. The node ID defaults to 10 (see Node ID) and the bus runs classic CAN at 1 Mbit/s with 29-bit identifiers. The node answers GetNodeInfo (software version and git commit, with the chip's unique ID), GetSet and ExecuteOpcode for its parameters, RestartNode, and the `etherform.Echo` link test service (type ID 106, `messages/etherform`).

## Mode and actuator ID selection (J5)
J5 is a 2x4 header (1.27 mm pitch). Each of its four rows has a signal pin (odd pin numbers 1, 3, 5, 7) beside a ground pin (even pin numbers). Every signal pin has a 10 kOhm pull-up to 3.3 V, so an open row reads high and a jumper across the row (signal to ground) pulls it low. The pins are read once at start-up, so reset or power-cycle the board after changing a jumper.

| J5 pin | Signal | MCU pin | Function |
|--------|--------|---------|----------|
| 1 | GPIO1 | PA8 | Mode: jumper fitted = servo (ArrayCommand), open = motor (RawCommand) |
| 3 | GPIO2 | PB2 | Actuator ID offset bit 0 (LSB), jumper fitted = 1 |
| 5 | GPIO3 | PB1 | Actuator ID offset bit 1, jumper fitted = 1 |
| 7 | GPIO4 | PB0 | Actuator ID offset bit 2 (MSB), jumper fitted = 1 |

The three offset bits give an offset of 0 to 7. PWM output 0 (J4 pin 8) answers actuator id = offset, output 1 (pin 6) offset + 1, output 2 (pin 4) offset + 2 and output 3 (pin 2) offset + 3. The highest actuator id reachable with the jumpers is therefore 10, so to use more than 11 actuators a SW offset must be set (See Building and Flashing).


## Motor mode commands
RawCommand values from 0 to 8191 map linearly to a 1000 to 2000 us pulse. Negative values are not supported (there is no meaningful PWM for them) and are treated as 0.

## PWM timing calibration
The PCA9685 generates the PWM from its internal oscillator, which is only accurate to about +-10 %, so the period and every pulse width are off by the same factor on a board that has not been calibrated. A board measured at the default `PWM_PRESCALE` of 121 had a 18.6 ms period (53.8 Hz) and a 926 us idle pulse instead of 20 ms and 1000 us. Calibrate each board against a scope (or the logic analyser) reading of the period at the default:

    new PWM_PRESCALE = round((121 + 1) * 20000 / measured_period_us) - 1      (18600 us gives 130)

then `tools/can_pwm_param.py 10 set PWM_PRESCALE <value>`. The change applies at once (the outputs pause for about a millisecond) and is kept across restarts. Writing 0 restores the default of 121.

## Motor arming at start-up
Many ESCs need to see the zero throttle pulse (1000 us) once before they arm, so a raised `MOTOR_MIN_US` would stop them arming. If `MOTOR_ARM_MS` is set (100 to 10000 ms, default 0 = off) the board, in motor mode, holds all four outputs at 1000 us for that long after power-up so the ESCs can arm, then idles them at the configured minimum pulse width (`MOTOR_MIN_US_0..3`) until commands arrive. RawCommand messages received during the arming time are ignored. The setting is read at start-up, so restart the node after changing it. Servo mode does not arm.

## Motor mode timeout
In motor mode (J5 pin 1 open), if no RawCommand message is received for 5 seconds all four PWM signals are switched off (held low, as after power-up). They resume with the next RawCommand. Servo mode has no timeout: each output keeps its last commanded pulse width.

The timeout is programmable with the `MOTOR_TIMEOUT_MS` parameter (100 to 60000 ms, stored in flash, applied immediately). Writing 0 restores the default, `default_motor_timeout_ms` in `board/user_defined_threshold.h` (5000 ms).

What the timeout does is set by `MOTOR_TIMEOUT_ACTION`: 0 (the default) switches the PWM signals off, 1 holds the minimum pulse width (zero throttle) instead, which keeps an ESC armed. Some ESCs react to the signal disappearing; use 1 if yours does.

## Pulse width limits and motor timeout
The pulse width limits that scale the commands are programmable over CAN, as parameters (type `uavcan.protocol.param.GetSet`, integer, microseconds). They are stored in flash, applied immediately and kept across restarts. Writing 0 to a parameter (or erasing, or an unwritten page) goes back to the default, which is the constant in `board/user_defined_threshold.h` (1000 us minimum, 2000 us maximum).

| Parameter | Used by |
|-----------|---------|
| `SERVO_MIN_US_0` to `_3` | Servo commands: UNITLESS -1 maps to this pulse width on output 0 to 3, and PWM commands are limited to at least this |
| `SERVO_MAX_US_0` to `_3` | Servo commands: UNITLESS +1 maps to this pulse width, and PWM commands are limited to at most this |
| `MOTOR_MIN_US_0` to `_3` | RawCommand 0 |
| `MOTOR_MAX_US_0` to `_3` | RawCommand full scale (8192) |

Values must be 1 to 20000 (one 50 Hz period). A change that would leave an output with a maximum that is not above its minimum is ignored, so when moving a range up, set the maximum first. PWM-type servo commands (command_type PWM) are limited to the same servo range, so a pulse width outside it is clamped to the minimum or maximum.

The DroneCAN GUI tool can edit them, or use `tools/can_pwm_param.py` (needs `pip install dronecan pyserial` and a serial USB-CAN adapter):

```bash
tools/can_pwm_param.py 10 list                       # every parameter of node 10
tools/can_pwm_param.py 10 set-range motor 0 1100 1900 # both limits of motor output 0
tools/can_pwm_param.py 10 set SERVO_MAX_US_2 1800
tools/can_pwm_param.py 10 set MOTOR_TIMEOUT_MS 2000   # motor mode timeout, ms
tools/can_pwm_param.py 10 erase                      # back to the defaults (also the node ID and the motor timeout)
```

## Motor ramp test
`tools/motor_ramp.py` ramps the RawCommand value 0 -> max -> 0 on the outputs through the serial USB-CAN adapter (motor mode needs J5 row 1 open; requires `pip install dronecan pyserial`). Remove the propellers first. For example `tools/motor_ramp.py --max 1600` is a gentle ramp to about 20 %, and `--max 8191` is the default maximum. With the J5 row 1 jumper fitted (servo mode) add `--servo` to send ArrayCommand instead, as UNITLESS (`--type unitless`, the default) or PWM (`--type pwm`) commands; the same ramp then gives 1000 us at 0 and 2000 us at full scale with the default limits.

## Fault handling
* **PCA9685 (I2C):** I2C timeouts are 20 ms. If a write to the PCA9685 fails, the node reports NodeStatus health ERROR with vendor specific status code 1, skips further writes, and every second re-initializes the I2C peripheral and the PCA9685. When it answers again the health returns to OK and the outputs are restored to their last commanded state.
* **CAN bus-off:** after a bus-off the controller is restarted every 100 ms until it rejoins the bus.

## Node ID
J5 is used for the mode and actuator ids, so the node ID defaults to 10. It can be changed over CAN with the standard DroneCAN parameter services (for example from the DroneCAN GUI tool):

* Write the integer parameter `NODE_ID` (1 to 127) with `uavcan.protocol.param.GetSet`. The value is stored in the last flash pages (61 to 63 are reserved by the linker script) and is used after the node restarts. Values outside 0 to 127 are ignored.
* Restart the node with `uavcan.protocol.RestartNode` (or power-cycle it) to apply the new ID.
* Writing 0 removes the stored ID so the default of 10 is used again. `uavcan.protocol.param.ExecuteOpcode` with the erase opcode removes the stored ID and the stored pulse width limits.

Writing flash stops the processor for a few tens of milliseconds, so do not change the ID while the actuators are in use.

## Python tools
The scripts in `tools/` talk to the board through a serial USB-CAN adapter (`pip install dronecan pyserial`) or an ST-LINK:

| Script | Purpose |
|--------|---------|
| `flash_and_check.py` | Program, verify and check a board over SWD and CAN (also run by `make flash`); set or clear the node ID or all settings |
| `can_pwm_param.py` | List, read and set the parameters (node ID, pulse width limits, motor timeout), erase them, restart the node |
| `can_getnodeinfo.py` | Read GetNodeInfo (name, version, health) from a node |
| `motor_ramp.py` | Ramp the outputs 0 to full scale and back, in motor or servo mode, for bench tests (remove the propellers first) |

## Firmware version
The version is set in the top level `CMakeLists.txt` (`FIRMWARE_VERSION_MAJOR/MINOR/PATCH`). Every build also records the git commit it was built from, and whether the working tree had uncommitted changes, e.g. `0.3.0+1a2b3c4d-dirty`. The version is available in two places:

* **Over CAN:** `uavcan.protocol.GetNodeInfo` reports the major and minor version and the commit (`tools/can_getnodeinfo.py` prints them).
* **In flash:** a 48 byte block (`board/Fw_info.h`) sits right after the vector table, so the version can be read over SWD even if the board is not on a CAN bus. `tools/flash_and_check.py` shows the firmware on the board and the firmware it is about to program, and fails if the board reports something else after programming.

GetNodeInfo also reports the hardware version: the major number is the board revision (Rev A = 1, Rev B = 2, and so on), set by `hw_version_major` in `board/Canard_pwm_node.h`. The board cannot detect its revision at run time, so it is fixed for the revision the firmware is built for (currently Rev B).

Bump the version in `CMakeLists.txt` for every release; a build from a tree with uncommitted changes carries `-dirty`, so a release should be built from a clean checkout.

# Building and Flashing
The software can be built for two different architectures: STM32 (the firmware, loaded onto EFI's HW) and HOST (the unit tests, which run on the PC). Configuring downloads libcanard, the DroneCAN DSDL files, the code generator and the ST HAL at pinned commits, and runs the generator in a Python virtual environment, so it needs network access, Python 3 with `venv`, and CMake 3.15 or newer.

## STM
Note that cmake will use the STM architecture by default. The build needs `arm-none-eabi-gcc` on your PATH, or set `ARM_TOOLCHAIN_DIR` to the directory containing it (e.g. the `tools/bin` folder of STM32CubeIDE's GNU Tools for STM32 plugin). The build type defaults to `MinSizeRel`; the other build types are too large for the 122 KB flash region.

```bash
mkdir build\_stm
cd build\_stm
cmake .. -DARCH=STM
make
```

After connecting an appropriate USB based STM32 flasher (e.g. STLINK-V3MINNIE):

```bash
make flash
```

This runs `tools/flash_and_check.py`, which programs and verifies the firmware over SWD with OpenOCD, resets the board and checks that it works (see below). It needs Python 3 and OpenOCD; the copy that ships with STM32CubeIDE is found automatically, otherwise put `openocd` on the PATH or set `OPENOCD` and `OPENOCD_SCRIPTS`. Pass extra options to the script with `-DFLASH_ARGS`, for example `cmake .. -DFLASH_ARGS="--can-device none"`.

The SW is now loaded on your HW. 


### Programming and checking boards with `tools/flash_and_check.py`

For one board at a time, this script (also run by `make flash`) programs the firmware over SWD with OpenOCD, resets the board and checks that it works. The CAN check also needs `pyserial` and a serial USB-CAN adapter; it is skipped if either is missing.

```bash
tools/flash_and_check.py                       # program the newest build, then check it over CAN
tools/flash_and_check.py --elf path/to/can_pwm_firmware.elf
tools/flash_and_check.py --check-only          # do not program: just read and check the board
tools/flash_and_check.py --can-device none     # program only, no CAN check
tools/flash_and_check.py --set-node-id 42      # also store node ID 42 (1 to 127)
tools/flash_and_check.py --clear-node-id       # also remove a stored ID (back to the default of 10)
tools/flash_and_check.py --clear-settings      # also erase the node ID, pulse width limits and motor timeout
```

What it does, in order:

1. Reads the stored node ID and PWM settings, the J5 pins (mode and actuator ID offset) and the chip's unique ID.
2. Programs and verifies the firmware. The settings pages (flash pages 61 and 62) are not touched, so stored settings survive a firmware update unless you ask for them to be cleared.
3. Resets the board and works out which node ID it should be using: the stored ID, otherwise 10.
4. Asks that node for `GetNodeInfo` over CAN and checks that the reply is valid and the health is OK (health ERROR with vendor status 1 means the PCA9685 is not answering).
5. Prints **PASS** or **FAIL** and exits with 0 only for PASS.

Other options are `--probe-serial` to choose one of several ST-LINKs, `--interface` and `--stock` for a stock OpenOCD (the CubeIDE copy needs the defaults), and `--boot-wait` to allow a slow start. A board that is not on the CAN bus fails the check even though it was programmed correctly; use `--can-device none` for that case. The J5 mode shown is the pin state at the time it is read; the board applies it at start-up.

## Host unit tests
```bash
mkdir build_host
cd build_host
cmake .. -DARCH=HOST
make
./tests/pwm_tests
```
These test `Pwm_config.h`: the pulse width limits, the servo and motor command arithmetic (including clamping and negative motor commands), the parameter names and the validation of programmed values.

# Testing on hardware
Boards are tested through a serial USB-CAN adapter (any adapter that speaks the same 20 byte serial protocol, tested with the product below) or an ST-LINK, using the Python tools above:

![Board](images/usbcan.png)
https://www.electromaker.io/shop/product/usb-can-analyzer?srsltid=AfmBOoo8ui31hktLYzUtisjxzqUPLeP86UoOVy075a30c6nakciVkjo-

* `tools/flash_and_check.py` programs a board and checks that it answers GetNodeInfo with health OK.
* `tools/can_pwm_param.py` reads and sets the parameters.
* `tools/motor_ramp.py` drives the outputs through the whole range (remove the propellers first).

The USB-CAN adapter drops frames now and then, so the tools repeat requests; a single "no reply" does not mean a fault.
